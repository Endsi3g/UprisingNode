## 2024-05-18 - Database Aggregation over In-Memory Processing
**Learning:** Found a major performance bottleneck where the application was fetching all user leads (`findAll`) into Node.js memory just to calculate derived stats (counts, sums) via array `.filter()` and `.reduce()`. This creates an O(N) memory and processing bottleneck that gets progressively worse as the database grows. Also, using wildcard eslint-disables without `.next-line` causes linting configuration bleeding.
**Action:** Replace `findMany()` combined with memory-based maps/reduces with Prisma database-level functions like `aggregate({ _sum: { ... } })` and `count()` to execute optimizations directly on the DB. When typing controllers, create and import `AuthenticatedRequest` to avoid `req: any` and overly broad `eslint-disable` usage. Always ensure multiplier constants from the original filtering logic (e.g. `* 10` for score mapping) are applied to database aggregation results.
